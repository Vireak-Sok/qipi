# Qipi application structure

## Rendering ownership

`src/ui/QipiShell.jsx` is a Next server component. `PageSurface` renders a native element for each region, with static markup supplied by modules under `src/ui/pages/` and `src/ui/components/`. Navigation, page headings, and dialogs use shared factories. `public/index.html` is generated by `pnpm generate:shell` (also before dev/build); edit the modules instead of the generated document.

The existing browser controllers own the contents of those static regions. The shared `trip-card.js` renderer is used by feed, search, profile, and Saved. This is an incremental architecture, not a completed conversion of every interaction to React hooks. Do not add React state that reconciles descendants also mutated by a DOM controller. When migrating a region to a client component, move its event handlers and renderer together, then remove the old controller's ownership of that region.

## URL contract

`public/js/route-config.js` owns named paths, reserved segments, URL constructors, and supported page shapes. Next rejects malformed multi-segment page paths. Client navigation and refresh use the same route definitions.

| Resource | URL |
| --- | --- |
| Feed, explore, upcoming trips, settings | `/feed`, `/explore`, `/trips`, `/settings` |
| Search | `/search?q=...` |
| Profile | `/:username` |
| Own profile collections | `/:username?tab=saved` or `?tab=joining` |
| Post detail | `/post/:id` (existing detail dialog) |
| Public registered image | `/media/:id` |
| Old Saved link | `/saved` opens own profile's Saved tab after sign-in |

Public profiles are stored independently of posts. `PUT /api/me/profile` synchronizes only public fields from the server-verified Supabase user and preserves the assigned username when a display name changes. Existing ID-based and derived demo links still resolve. A new member becomes discoverable after their first authenticated application session; accounts that have never opened Qipi are not backfilled automatically.

Saved IDs retain the existing device-local browser storage. The owner-only tab is a UI collection, not server-side cross-device bookmarks. Old saved IDs remain intact. Moving this to per-user storage later needs an authenticated bookmark repository and an explicit import of legacy device bookmarks.

## Data boundaries

The client API adapter handles session headers, structured errors, 15-second timeouts, optional cancellation, and in-flight GET coalescing. It does not cache across completed requests or accounts. Profile and Saved controllers ignore stale responses. Saved requests are batched in groups of 100 IDs, and the server validates/filter IDs before serialization. `GET /api/trips?limit=20` supports stable keyset paging with `nextCursor`; omitting `limit` keeps the original full-list response for current clients. Trip cards in list responses also use batched like and approved-join counts to avoid rescanning those arrays for each trip.

Server route modules depend on the store interface, not browser state. Supabase Auth verification remains authoritative. Deployed Vercel instances require the configured Supabase URL, publishable key, and server-only secret key. The local JSON fallback remains development-only.

## Scaling work that still needs a data migration

The current Supabase adapter intentionally keeps the existing `qipi_state` JSONB record and compare-and-swap writes compatible. Splitting source files does not remove this record's contention or full-record reads. Before sustained growth:

1. Migrate profiles, posts, joins, reactions, follows, and bookmarks to separate indexed tables, with unique usernames, foreign keys, and explicit access policies.
2. Move feed/search filtering and cursor pagination into SQL; add pagination to the UI without changing card components.
3. Replace process-local write limiting with shared rate limiting, and add request/error monitoring.
4. Add a migration/backfill check that compares counts and public API responses before switching store adapters.
5. Move one controller-owned region at a time to React client components, preserving these route and API contracts.

No live schema migration or deployment is performed by this refactor.

## Checks

`pnpm test` covers ownership, dynamic routes, Saved visibility, profile slug stability, request coalescing, API/auth behavior, media access, and unique shell IDs. `pnpm build` generates the static fallback and builds Next. `pnpm check:production` runs the production build against disposable Supabase-compatible endpoints; it does not contact the live Supabase project.
